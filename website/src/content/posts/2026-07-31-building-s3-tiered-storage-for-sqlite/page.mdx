Every Rivet Actor gets its own isolated SQLite database. It's the core of how Rivet Actors store data: it's built on standards instead of a proprietary storage API, and agents are great at generating SQL. SQLite is the technology that makes actors just work, with migrations, performance, and flexibility. It's also single-writer, which fits actors perfectly, since there's only one actor writing to each database at a time.

Common use cases of SQLite in Rivet Actors include:

- **Agent sessions**: store session transcripts in SQLite.
- **Agent memory**: durable, long-term agent memory.
- **A database per tenant**: full tenant isolation without running a very expensive Postgres server per customer.
- **Local-first sync and CRDT multiplayer**: each document keeps its own operation log to sync against.
- **Audit logs and edit history**: append-heavy tables that grow frequently but are rarely read.
- **Infrastructure components**: things like queues, workflows, and scheduling are all easy to build on top of this.

## The constraints that drive a novel SQLite architecture

When designing SQLite for actors, we looked at a lot of off-the-shelf options such as Litestream and LiteFS, and none of them quite fit the bill. It came down to seven main constraints that caused us to build a new SQLite storage layer from the ground up:

1. **Fast, durable writes**: How fast data can be written to the SQLite database directly impacts user-facing performance. Writes must return in low milliseconds while still maintaining at least double redundancy, so a node can fail without causing an outage.
2. **Bottomless storage**: One of the best-known constraints of Durable Objects is its 10 GB database cap, meaning that if you have a database per tenant and that tenant's data grows, you'll have a complete outage when you hit that size limit. That's not an option for Rivet Actors.
3. **Billions of databases per cluster**: Rivet Actors get created at very high frequency, for everything as coarse as agent sessions to as granular as every user that visits a site or individual background jobs. Creating actor databases has to be cheap, and there are going to be a lot of them.
4. **An idle database costs no resources**: When an actor goes to sleep, the only resources its database takes should be disk or S3, not live resources like you get with a Postgres server.
5. **Fast failover**: If an actor crashes, upgrades, or migrates for any reason, it must come back online immediately without any restore step.
6. **Self-hostable with no proprietary dependencies**: There must be no dependencies on proprietary cloud services, and it must be easily self-hostable in a range of environments, from local development to highly scalable distributed environments.
7. **No new database to operate**: The engine must not require running a new stateful database. All state lives in storage systems teams already run, such as Postgres, RocksDB, FoundationDB, and S3, with the SQLite engine as stateless logic on top.

This post will discuss what we've built so far with the new tiered storage SQLite engine we've implemented for Rivet.

## How tiered storage usually goes wrong

There are four common ways databases fall short or cheat on these constraints:

1. **Commit straight to object storage**: Every commit becomes a PUT request to S3, and those requests answer in roughly 30 to 45 milliseconds. This has two main problems:
   - The latency is way too high for database writes. You should not be waiting 35 milliseconds for a database write. For example, turbopuffer documents ~285 ms p50 writes and WarpStream ~400 ms p99, which is fine for their workloads, but not for a SQLite commit sitting inside a user-facing request. S3 Express One Zone can bring this down to single-digit milliseconds, but it is expensive and doesn't run anywhere outside of AWS, which breaks our self-hosting constraint.
   - It is excessively expensive to make an S3 write for every commit. There are workarounds like coalescing writes, but the point still stands.
2. **Skip durability in favor of write performance**: Data needs at least double redundancy so that there are no outages or lost data when you write to SQLite. Some options advertise fast write performance, but the writes go to a local SSD without proper redundancy, which risks data loss and outages.
3. **A single point of failure for writes**: Options like SlateDB provide an easy way to do S3 tiered storage, but are designed around a single writer, creating a single point of failure that requires complicated sharding to scale horizontally. We wanted a more flexible and easier to operate architecture.
4. **Persistent servers per database**: Some options let you assign each database to a dedicated server. This works at a few hundred databases, but breaks down at billions of mostly idle databases, where balancing them across stateful servers does not play nice.

## A virtual filesystem instead of a network filesystem

Before jumping into the details of tiered storage in Rivet, we first need to understand how Rivet uses a virtual filesystem for SQLite.

Most cloud VMs sit on a network-attached block device like EBS, meaning that all filesystem operations go to a separate machine that serves the reads and writes. This is fine for most use cases, but we needed something more flexible in terms of performance and portability that's not tied to a specific cloud's architecture.

Rivet does not use network-attached block devices at all. Instead, the storage layer is brought up to the application layer by implementing a [virtual filesystem](https://www.sqlite.org/vfs.html) for SQLite.

The SQLite virtual filesystem lets your application implement custom functionality for reading and writing database pages. SQLite talks to its filesystem through a small interface of methods like `xOpen`, `xRead`, `xWrite`, and `xSync`, all operating on the database file in pages. Rivet's VFS is written in Rust and implements that interface against the storage layer instead of a disk: `xRead` fetches pages from storage, `xWrite` stages dirty pages in memory, and `xSync` commits them to the storage layer as a single batched, durable write. On top of this interface, Rivet adds intelligent caching and prefetching to achieve high-performance SQLite.

With the virtual filesystem, instead of needing the entire database to already sit on disk, the database can be lazy loaded. Combined with intelligent prefetching, this makes it possible to instantly start an actor on a machine that does not already have its database, while providing near-in-memory performance for SQLite.

The Rivet virtual filesystem for SQLite provides:

- **Fast, durable writes**: Writes are coalesced and batched when written to the storage layer.
- **Pluggable storage medium**: Rivet supports three storage backends: RocksDB, Postgres for small deployments, and FoundationDB for large deployments. The VFS lets us plug into any of those, which keeps Rivet easy to self-host.
- **Lazy loading for bottomless storage**: Because pages can be read in lazily, SQLite databases get bottomless storage without the 10 GB cap that Durable Objects have.
- **No resources when sleeping**: Because the VFS can start a database instantly, no resources are required to maintain the database while the actor is sleeping.
- **Lazy loading provides fast failover**: Because a database can start without loading the entire thing onto the machine, a Rivet Actor can fail over to another machine immediately.
- **Enables elastic compute**: Because actors can start up instantly, we can easily scale compute up and down as actors wake up and go to sleep, instead of having compute sitting idle for actors that are not active.

The virtual filesystem satisfies the seven constraints above. However, until now, it required storing all SQLite data on an SSD using whichever storage layer is plugged in (FoundationDB, Postgres, or RocksDB).

## The cost benefit of tiered storage

The hot tier is built for write latency with fast and cheap reads and writes, but at the cost of expensive storage. This can be solved by offloading data to S3 when it goes stale, meaning that hot data can be stored in the faster, more expensive tier (RocksDB, Postgres, or FoundationDB) while data that is not frequently accessed can be offloaded to S3.

| Storage | $/GB-month | 5 TB stored | Write 1 GiB | Read 1 GiB |
|---|---|---|---|---|
| Block storage, replicated 3x (EBS gp3) | $0.24 | $1,230 | Included | Included |
| S3 Standard, replication included | $0.023 | $118 | ~$0.02 | ~$0.002 |

We price block storage at 3x because we assume triple redundancy for writes in the hot tier, while S3 Standard provides replication as part of its default pricing. The S3 write cost assumes 256 KiB objects, which we'll come back to below.

As the table shows, the hot tier costs roughly 10x as much as S3 for storage, but its reads and writes cost nothing per operation, while S3 bills every request. This makes the hot tier the right place for data you read and write frequently, while less frequently accessed data can be offloaded to S3 automatically.

Common actor workloads with data that can be offloaded to S3:

- **Agent sessions**: you want an archive of every agent session, but old sessions are rarely opened again.
- **CRDT documents**: you want to preserve a document's full operation log, but old operations are rarely replayed.
- **Audit logs and edit histories**: you write a lot of data, but rarely access the history, so it can sit in cold storage.
- **Ledgers**: the current balance is hot, last year's entries are not.

## Adding a cold tier to SQLite

We've covered how data gets in and out of the hot path with the virtual filesystem. Now let's dig into how tiered storage is added on top. Reads and writes always go to the hot storage layer for the best performance, and data is offloaded to S3 in the background once it goes cold.

The cold storage system in the SQLite engine has two components:

- **The compactor**: finds chunks of Rivet databases that have not been touched for 7 days (configurable) and offloads them from hot storage to S3.
- **Rehydration on read**: when cold data is read, it is rehydrated into the hot tier, then offloaded back to the cold tier or deleted as needed.

With the cold tier added, a chunk can now live in three places: SQLite's in-memory page cache, hot storage, or cold storage on S3.

This architecture supports our original design constraints:

- **Instant startup of actors**: Because chunks are lazy loaded from S3, an actor that has not been accessed for years can still start up instantly.
- **S3-compatible and runs on any cloud**: Self-hosted clusters can point the cold tier at anything with an S3 API, such as AWS S3, Google Cloud Storage, Cloudflare R2, MinIO, and so on.
- **Billions of databases per cluster**: Because large amounts of data can be stored cheaply on S3 instead of on hot disk, it's possible to have billions of actor databases in storage.

## Backups and point-in-time recovery, for free

In addition to being a cost-efficient, scalable way of storing actor data, S3 is also an industry-standard place for backing up databases. This means the cold storage engine in Rivet doubles as a backup mechanism for the database.

Rivet also provides point-in-time recovery with configurable granularity and retention, which lets you recover a database from a point in time from S3. Point-in-time recovery is optional, as it does require more storage.

## Seven constraints, satisfied

1. **Fast, durable writes**: commits go to the replicated hot tier and return in low milliseconds. S3 never sits on the write path.
2. **Bottomless storage**: cold chunks offload to object storage with no hard database ceiling.
3. **Billions of databases per cluster**: a database is rows in a shared storage layer, not a volume plus a filesystem plus a process.
4. **An idle database costs no resources**: a sleeping database costs nothing when idle. No process, no CPU, no memory, just storage, and the cold majority of it at archive prices.
5. **Fast failover**: any machine can serve any actor by fetching pages. No volume attach, no restore.
6. **Self-hostable with no proprietary dependencies**: a pluggable hot tier (FoundationDB, Postgres, RocksDB) and an S3-compatible cold tier.
7. **No new database to operate**: the hot tier runs on databases teams already operate, the cold tier is any S3-compatible store, and the engine itself holds no state of its own.

## FAQ

**Can this SQLite layer be used without Rivet Actors?**

The core components are trivial to split out, since the engine already supports native SQLite and UniversalDB over any transport. It would require splitting out the depot-client and depot libraries and running the protocol over a new network transport. Please let us know if you do this, we would love to support this use case. However, we believe Rivet Actors are the best way to work with SQLite anywhere, since actors provide single-writer semantics at their core.

**How does it handle multiple writers?**

It doesn't. Actors are single-writer by design: there can only be one instance of a given actor running at a time. As a fallback, there is a guard preventing dual writes.

**You're running SQLite on Postgres?**

Yes. Rivet's storage layer is meant to be flexible enough to run anywhere. Most teams know how to operate Postgres or already have a managed Postgres deployment, so it's plug and play.
