Every Rivet Actor gets its own isolated SQLite database. One database per user, per agent session, per document. At that granularity you are not managing thousands of databases, you are managing billions.

This post is about the storage engine underneath: how writes stay fast and durable, how a sleeping database costs nothing, and why we built **tiered storage to S3** instead of running SQLite directly on object storage.

## SQLite in Rivet Actors

Rivet is built on standards. Actors persist to plain SQLite with plain SQL, not a proprietary storage API, so everything that already speaks SQLite works, including [Drizzle ORM](/docs/actors/sqlite-drizzle).

SQLite fits actors unusually well because an actor is a **single writer**. With one owner per database there is no lock contention and no connection pool, which is [where SQLite is fastest](/blog/2025-02-16-sqlite-on-the-server-is-misunderstood/). It handles the data shapes these workloads actually produce: mutating rows in place, plain JSON documents, and key-value access.

A database per actor changes what you can build:

- **Agent sessions**: one session's transcript, tool calls, and memory in one database.
- **Agent memory**: durable long-term state an agent can query with SQL.
- **A database per tenant**: full isolation without running a Postgres server per customer.
- **Local-first sync and CRDT multiplayer**: each document or lobby keeps its own op log to sync against.
- **Audit logs, telemetry, and history**: append-heavy tables that grow forever and are rarely re-read.

## Six design constraints

Billions of small databases put six constraints on the storage engine at once.

**Scale:**

1. **Fast, durable writes.** A commit blocks a user-facing request, so it must return in low milliseconds. Once it returns, it must survive process loss, power loss, and losing the machine.
2. **Bottomless storage.** No per-database ceiling. Transcripts and logs grow forever.
3. **Billions of databases per cluster.** Per-database overhead must be near zero.

**Lifecycle:**

4. **No CPU or memory when sleeping.** An idle database costs storage and nothing else.
5. **Fast failover.** When a machine dies, its actors come back somewhere else immediately. No restore step, no volume copy.

**Deployment:**

6. **Self-hostable.** No hard dependency on a single proprietary cloud service.

Constraints 1 and 2 pull against each other. The only storage that is bottomless and archive-priced is object storage, and object storage is the one storage that cannot return a commit in milliseconds.

## How this usually goes wrong

There are three common ways databases cheat on that tension.

**Commit straight to object storage.** Every commit becomes a PUT, and S3 answers small requests in roughly 30 to 45 ms at the median, worse at the tail. Some systems accept this honestly and say so: turbopuffer documents ~285 ms p50 writes and WarpStream ~400 ms p99 produce latency, which is fine for search indexing and streaming where latency amortizes. A SQLite commit sits inside a user-facing request. It does not amortize.

- The escape hatch is S3 Express One Zone at single-digit milliseconds, but it costs $0.11/GB-month (more than the block storage you were trying to avoid), lives in a single availability zone, and is AWS-proprietary. That fails cost, redundancy, and self-hosting in one move.

**Write to a local SSD and call it durable.** The fsync is fast, but if the data is not replicated before the commit returns, losing the machine loses every commit since the last backup.

**Keep a process resident per database.** A dedicated server, pod, or connection pool per tenant burns CPU and memory while idle. That works at hundreds of databases and fails at billions.

And even if you accept object-storage latency, request pricing punishes small writes: uploading data as 4 KiB database pages costs **$1.31 per GiB in PUT requests alone**, dwarfing the $0.023 that GiB costs to store for a month. Hold that thought.

## A virtual filesystem instead of a network filesystem

Start with how a database is stored while it is hot.

Most cloud databases sit on a network-attached block device like EBS. The database believes it has a local disk, every read and write is secretly a network hop, and the volume is pinned to one machine in one zone. That is workable for one big database. For billions of small ones it is a dead end, because every database drags a volume, a filesystem, and an attachment along with it.

Rivet does not use a disk abstraction at all. SQLite has a pluggable filesystem interface called the [VFS](https://www.sqlite.org/vfs.html), and every actor's database runs on a custom Rivet VFS that talks directly to a storage layer:

- **Reads are explicit page fetches.** SQLite asks for the exact pages it needs, and the VFS pulls them from the storage layer and caches them in memory. Repeated reads hit SQLite's page cache at memory speed.
- **Commits are batched writes.** A transaction's dirty pages go to the storage layer as one replicated write, and the commit returns once it is durable. That is low milliseconds, not an S3 round trip.
- **The storage layer is pluggable.** FoundationDB on Rivet Cloud, Postgres or RocksDB when self-hosting. On Rivet Cloud the storage tier runs on locally-attached NVMe, the same approach as PlanetScale Metal, so page reads are backed by microsecond-class flash rather than a network block device.

Because there is no volume, compute becomes elastic:

- An actor can wake on **any machine** in the cluster with no volume attach and no data copy. It lazily pulls only the pages it touches.
- Failover is the same operation as waking up. A machine dies, the actor starts elsewhere and reads its pages. No restore step.
- A sleeping actor is nothing but rows in the storage layer. No process, no CPU, no memory.

That satisfies five of the six constraints. Fast durable writes, billions of databases, nothing when idle, fast failover, and self-hostable backends. The one left is bottomless.

## The hot tier is the expensive part

The hot tier is built for write latency, and you pay for that per byte. Using EBS gp3 as the reference price for fast, durable block storage (Hyperdisk Balanced on Google Cloud is about the same):

| Storage | $/GB-month | 5 TB per month |
|---|---|---|
| Block storage (EBS gp3) | $0.08 | $410 |
| Block storage, replicated 3x | $0.24 | $1,230 |
| S3 Standard, replication included | $0.023 | $118 |

Durable means replicated, so the honest block-storage number is the 3x row: roughly **10x the price of S3** for the same bytes.

Agent workloads generate exactly the data that makes this hurt. Transcripts, tool-call logs, memory, telemetry. Most of it is written once, read for a few days, and then almost never touched again. Keeping all of it on the fast tier forever means paying the write-latency premium on data that no longer needs it.

## Tiering to S3

So the storage engine tiers: this is **tiered storage, not S3-backed storage**, and the difference is which tier accepts the write. Writes always land in the hot tier. S3 is never on the commit path.

- Data is tracked in **chunks** (a chunk is a group of database pages, 256 KiB).
- When a chunk goes untouched for **7 days** (configurable), a background compactor coalesces it into an object, uploads it to object storage, and evicts the hot copy.
- Tiering is **sub-database**. The same database can hold this week's rows in the hot tier and last year's rows in S3 at the same time.
- Reading a cold chunk fetches it from object storage once (tens of milliseconds) and rehydrates it into the hot tier, where it is fast again.

Coalescing into chunks is also what makes the economics work:

- Uploading 256 KiB chunks costs about **$0.02 per GiB in PUT requests**, 64x cheaper than uploading page by page at $1.31 per GiB. Reading a GiB back costs about $0.002.
- Chunks clear S3's 128 KB minimum billable object size, so no byte is billed twice.
- The 7-day window means a frequently rewritten chunk is uploaded zero times instead of on every commit. Only data that has proven it is cold pays the upload toll, roughly once.

Two consequences fall out:

- **No hard database ceiling.** Databases are unbounded (the limit is configurable), unlike the 10 GB cap on Cloudflare Durable Objects. The hot tier holds the working set and object storage holds everything else.
- **S3-compatible, not S3-only.** Self-hosted clusters can point the cold tier at anything with an S3 API: MinIO, Cloudflare R2, Google Cloud Storage, and so on.

## What tiering is for

The workloads that fit actors are write-heavy and read-recent, which is the exact shape tiering rewards:

- **Agent transcripts**: append on every message, read the recent tail for context.
- **Audit logs and telemetry**: written constantly, read during an incident.
- **Document history and CRDT logs**: old operations are rarely replayed.
- **Ledgers**: the current balance is hot, 2019's entries are not.

The working set stays at memory and NVMe speed while the archive is priced like an archive, and data moves between the two automatically.

## Backups and point-in-time recovery, for free

Once chunks live in object storage as immutable objects, backups stop being a separate system:

- Every database gets **point-in-time recovery** with 5-minute granularity and 7-day retention by default (both configurable).
- Restoring to a point in time and forking a database are the same primitive: pick a timestamp, assemble that chunk set, start reading.
- Fork a production agent's database to replay a session, or restore one tenant without touching the rest.

## Six constraints, satisfied

1. **Fast, durable writes**: commits go to the replicated hot tier and return in low milliseconds. S3 never sits on the write path.
2. **Bottomless storage**: cold chunks offload to object storage with no hard database ceiling.
3. **Billions of databases per cluster**: a database is rows in a shared storage layer, not a volume plus a filesystem plus a process.
4. **No CPU or memory when sleeping**: a sleeping database **costs nothing when idle**. No process, no CPU, no memory, just storage, and the cold majority of it at archive prices.
5. **Fast failover**: any machine can serve any actor by fetching pages. No volume attach, no restore.
6. **Self-hostable**: a pluggable hot tier (FoundationDB, Postgres, RocksDB) and an S3-compatible cold tier.
