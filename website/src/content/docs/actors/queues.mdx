## What are queues?

- **Realtime**: messages are delivered to a live actor as soon as possible.
- **Durable**: messages are persisted and survive actor sleep/restart.
- **Observable**: every accepted send returns a receipt whose status can be checked later.
- **Scalable**: queues absorb large bursts and handle heavy backpressure safely.
- **Local per actor**: each actor instance has its own queue storage (scoped by actor key/id).

Queues are commonly referred to as "mailboxes" in other actor frameworks.

## What are queues good for?

- Great for any task that changes actor state.
- Separates asynchronous work from request lifetimes while keeping each delivery attempt durable.
- Makes complex behavior easier to organize.

## Delivery, retries, and dead letters

Automatic handlers use at-least-once delivery. Configure the total number of attempts and exponential backoff on the queue definition:

- A successful return from `onMessage` is an internal ack and produces `succeeded` status.
- A thrown error, rejected promise, or handler timeout is an internal nack. The message is retried until `maxAttempts` is reached, then becomes `deadLettered`.
- `onDeadLetter` is available only alongside `onMessage`. It is a durable notification callback; if it throws, it is retried independently and does not make the message live again.
- Both callbacks receive `{ signal }`. Timeout and actor shutdown abort this signal and the runtime stops waiting immediately. A late return or throw is ignored by the fenced delivery lease.
- Delivery is at least once, so make external side effects idempotent. A handler can finish an external write and stop before Rivet commits its ack.

There is no public `ack()`, `nack()`, or `complete()` method on a delivered message.

| Consumer API | Ack behavior | If user code throws | Timeout or crash |
| --- | --- | --- | --- |
| Queue `onMessage` | Returning successfully performs a fenced internal ack | Implicit nack, then backoff/retry or dead-lettering | Timeout aborts `signal` and immediately nacks without awaiting settlement; crash recovery retries an abandoned lease unless its final attempt was already used |
| `next()` / `nextBatch()` / `tryNext()` / `iter()` | Rivet atomically consumes before returning | Already consumed; it is not redelivered | Already consumed; it is not redelivered |

Catching an error inside `onMessage` and returning normally counts as success and therefore acknowledges the message. `waitForNames()` only waits for availability and does not consume or acknowledge anything.

`receipt.status()` is one nonblocking lookup. It can return `queued`, `delayed`, `processing`, `retrying`, `succeeded`, `deadLettered`, `consumed`, or `unknown`. Reconstruct a saved receipt with `handle.receipt(id)` on a client handle or `c.queue.receipt(id)` inside an actor. Terminal `succeeded` and `consumed` statuses are retained for 24 hours, subject to a per-actor cap; expired and unknown IDs return `unknown`.

Use `dedupeKey` to make repeated sends within the five-minute deduplication window resolve to the original receipt. Deduplication is scoped by the `(queue name, dedupeKey)` tuple.

## Pull messages with `next` and `nextBatch`

Use `next` when you want to wait for one queue message.
Use `nextBatch` when you want to wait for multiple queue messages.

- Waits until messages are available unless timeout is hit.
- Omit `timeout` to wait indefinitely.
- These raw pull APIs are only for queues without `onMessage`.
- Pulling is destructive and at-most-once: Rivet records `consumed` before returning the message. There is no ack or nack. If your code throws after `next()`, the message is not requeued.

## Sleeping behavior

If an actor has a `run` handler, it does not sleep while that handler is actively doing work. It only can sleep when the run loop is blocked waiting for queue entries (for example inside `iter(...)` or `next(...)`).

This means you can run normal code in `run` without worrying about sleep interrupting it mid-call.

## Debugging

- `GET /inspector/queue?limit=50` returns queue size and pending message metadata.
- `GET /inspector/summary` includes `queueSize` for quick queue health checks.
- `POST /queue/:name` returns a receipt ID after durable acceptance.
- `GET /queue/receipts/:receiptId` returns the current receipt status.
- In non-dev mode, inspector endpoints require authorization.

## Recommendations

- Actions are for getting data, queue entries are for mutating data.
- Implement connection auth in `onBeforeConnect`. See [Authentication](/docs/actors/authentication).
- Route most state changes through one queue loop so ordering stays predictable.
- If you need more complex multi-step run loops, consider using workflows.
- Use `c.aborted` and `c.abortSignal` for actor shutdown. Use your own `AbortController` for earlier loop cancellation.
- Use a workflow or an action when the caller needs a durable result or synchronous response. Queue receipts expose status, not handler return values.
