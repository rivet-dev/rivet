## How Versions Work

Each node has a **version number**. When you deploy new code with a new version, Rivet handles the transition automatically:

- **New actors go to the newest version**: When allocating actors, Rivet always prefers nodes with the highest version number
- **Multiple versions can coexist**: Old actors continue running on old versions while new actors are created on the new version
- **Drain old actors**: When enabled, a node connecting with a newer version number gracefully stops old actors so they are rescheduled to the new version
- **Versions only go up**: Deploying a lower version number never moves allocation back to it. To undo a bad deploy, redeploy the previous code with a new, higher version number.

<Note>
Versions are not configured by default. See [Setting the Version](#setting-the-version) to configure the node version.
</Note>

Worker versions are separate from public API versions. See [Backward Compatibility](/actors/docs/backward-compatibility) for action, queue, event, and stored-data changes during an upgrade.

## Configuration

### Setting the Version

Configure the node version with an environment variable or in your registry setup:

<CodeGroup>

```bash {{"title": "Environment Variable"}}
RIVET_ENVOY_VERSION=2
```

<CodeSnippet file="examples/docs/actors-versions/programmatic-version.ts" title="Programmatic" />

</CodeGroup>

<Warning>
The version **must** be set at build time, not at runtime. Do not use `Date.now()` or similar runtime values in your registry setup code. This would assign a different version every time the server starts, causing actors to be drained and rescheduled on every restart instead of only on new deployments.
</Warning>

<Warning>
The version **must** increase on every deployment. Never roll a deployment back to an older version number. New actors keep going to the nodes still on the higher version, so as the rollback replaces them the set of nodes accepting actors shrinks until it reaches zero and nothing can be scheduled. Allocation only recovers once every higher-version node has disconnected and expired. To undo a bad deploy, redeploy the previous code with a new, higher version number.
</Warning>

### Example Configurations

We recommend injecting a build-time value that increments with every deployment. Here are concrete examples for common setups:

<Tabs>

<Tab title="Dockerfile">

Generate the version at build time and bake it into the image as an environment variable:

```bash @nocheck
docker build --build-arg RIVET_ENVOY_VERSION=$(date +%s) .
```

```dockerfile @nocheck
FROM node:24-slim
ARG RIVET_ENVOY_VERSION
ENV RIVET_ENVOY_VERSION=$RIVET_ENVOY_VERSION
WORKDIR /app
COPY . .
RUN npm install && npm run build
CMD ["node", "dist/server.js"]
```

All containers from this image will share the same version.

</Tab>

<Tab title="Next.js">

Set the version in `next.config.ts`. Next.js evaluates this file once at build time and inlines the value into the bundle:

```typescript @nocheck
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  env: {
    RIVET_ENVOY_VERSION: String(Math.floor(Date.now() / 1000)),
  },
};

export default nextConfig;
```

</Tab>

<Tab title="Vite">

Use `define` in your Vite config. This is evaluated once at build time and inlined into the bundle:

```typescript @nocheck
import { defineConfig } from "vite";

export default defineConfig({
  define: {
    "process.env.RIVET_ENVOY_VERSION": JSON.stringify(
      String(Math.floor(Date.now() / 1000))
    ),
  },
});
```

</Tab>

<Tab title="CI/CD">

Set the version from your CI pipeline:

```yaml @nocheck
# GitHub Actions
env:
  RIVET_ENVOY_VERSION: ${{ github.run_number }}
```

```bash @nocheck
# Railway / Render / generic CI
export RIVET_ENVOY_VERSION=$(date +%s)
```

```bash @nocheck
# Git commit count
export RIVET_ENVOY_VERSION=$(git rev-list --count HEAD)
```

</Tab>

<Tab title="Build Script">

Generate a version file during your build step and import it:

```json @nocheck
{
  "scripts": {
    "build": "echo \"export const BUILD_VERSION = $(date +%s);\" > src/build-version.ts && tsc"
  }
}
```

```typescript @nocheck
import { actor, setup } from "rivetkit";
import { BUILD_VERSION } from "./build-version";

const myActor = actor({ state: {}, actions: {} });

const registry = setup({
  use: { myActor },
  envoy: {
    version: BUILD_VERSION,
  },
});
```

</Tab>

</Tabs>

### Drain on Version Upgrade

The `drain_on_version_upgrade` setting on a node pool controls whether old actors are stopped when nodes with a newer version connect. Set it when you create or update the pool. See [Nodes & Node Pools](/docs/nodes) for every pool setting, including how to rate-limit actor eviction during the drain.

```bash
curl -X PUT "$RIVET_API/pools/default?namespace=default" \
  -H "Authorization: Bearer $RIVET_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"drain_on_version_upgrade": true}'
```

| Value | Behavior |
|-------|----------|
| `false` (default) | Old actors keep running. New actors go to the new version. Versions coexist. |
| `true` | Old actors sleep, saving their state, and wake on a node running the new version. |

## Upgrading Actor State

When you deploy a new version, existing actors may need to handle schema changes in their persisted data.

### SQLite (recommended for complex schemas)

**Drizzle (recommended)**

Use [Drizzle](/actors/docs/sqlite-drizzle) for typed schemas with generated migrations. Drizzle generates versioned `.sql` migration files from your TypeScript schema and applies them in order automatically. This is the recommended approach when your schema evolves frequently.

**Raw SQL**

For actors using [raw SQLite](/actors/docs/sqlite), use `migrations` to apply numbered SQL steps in order. Give each schema its own migration table. RivetKit runs the returned `onMigrate` hook inside a SQLite savepoint, so the migration ladder is atomic:

### In-memory state (`c.state`)

If you use `c.state` for persistence, you are responsible for handling schema changes yourself. If you add, remove, or rename fields between versions, your code must handle the old shape gracefully.

## Advanced

### How Version Upgrade Detection Works

When `drain_on_version_upgrade` is enabled and a node connects with a newer version number, the control plane drains every older node in the same pool.

### SIGTERM Handling

When a node process receives `SIGTERM`, it gracefully stops all of its actors before exiting:

- Each actor's `onSleep` hook runs, giving it time to save state.
- Actors are rescheduled to other available nodes.
- If the process is killed before its actors finish stopping, for example with `SIGKILL`, the control plane reschedules them once the node is considered lost.

Give each node at least 60 seconds between `SIGTERM` and `SIGKILL`.

### Shutdown Timeouts

| Timeout | Default | Description | Configuration |
|---------|---------|-------------|---------------|
| `sleepGracePeriod` | 15s | Total graceful sleep budget for `onSleep`, `waitUntil`, `keepAwake`, and async raw WebSocket handlers | [Actor options](/actors/docs/lifecycle#options) |
| `envoy_lost_threshold` | 40s | How long the control plane waits before rescheduling the actors of a node that disappeared without stopping | [Control plane config](/docs/deploy/self-host/control-plane/configuration/) (`pegboard.envoy_lost_threshold`) |
