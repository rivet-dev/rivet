A Rivet JWT is a short-lived credential you mint on your backend and hand to an untrusted client. It carries a set of grants that say exactly what the holder may reach, and the control plane verifies it before routing any request.

Use one whenever a browser or mobile app talks to Rivet directly. For the wider picture of which credential to use where, see [Authentication](/docs/authentication).

## Issuing Tokens

`POST /auth/tokens` requires the admin token, so it can only be called from your backend.

```sh
curl -X POST "$RIVET_ENDPOINT/auth/tokens" \
  -H "Authorization: Bearer $RIVET_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "namespace": "production",
    "subject": "user_alice",
    "duration": 900,
    "grants": [
      { "resource": "actor_gateway", "target": { "id": "<actor-id>" }, "operations": ["read"] }
    ]
  }'
```

```json
{
  "token": "eyJhbGciOiJFZERTQSIsInR5cCI6InJpdmV0LWF1dGgrand0Iiwia2lkIjoi...",
  "issued_ts": 1758700000000,
  "expires_ts": 1758700900000
}
```

| Field | Required | Description |
| --- | --- | --- |
| `namespace` | Yes | Namespace name the token is scoped to. A token can never span namespaces. |
| `grants` | Yes | What the holder may reach. See [Grants](#grants). |
| `duration` | No | Lifetime in seconds. Defaults to `3600`, capped at `86400`. |
| `subject` | No | Your user identifier, up to 256 bytes. Opaque to Rivet; it appears in `sub` and in token inspection. |

## Grants

A grant answers one question: which operations may the holder perform on which resource.

```json
{ "resource": "actor_gateway", "target": { "id": "<actor-id>" }, "operations": ["read"] }
```

`target` is either `"any"` for every instance in the namespace, or `{ "id": "<id>" }` for one. `operations` is a subset of `create`, `read`, `update`, `delete`, and `list`.

| Resource | Gates |
| --- | --- |
| `actor_gateway` | Connecting to an actor by ID: actions, events, and raw HTTP or WebSocket handlers. |
| `actor` | Resolving or creating actors by key, and the actors API. |
| `actor_kv` | Reading an actor's raw KV, which the [inspector](/actors/docs/debugging) needs. |
| `namespace`, `runner`, `runner_config`, `datacenter` | Control-plane management APIs. |

### Resolving Versus Connecting

These are two different grants, and getting them confused is the most common mistake.

`getOrCreate(key)` and `get(key)` route through the query path, which checks `actor` with `create` and `read` respectively. Connecting to an actor you already have the ID for checks `actor_gateway` with `read` on that ID.

That distinction is what makes tight scoping possible. A token holding only `actor_gateway` `read` on one ID can reach that actor and nothing else. It cannot create actors, cannot list them, and cannot guess its way to another one.

<CodeSnippet file="examples/docs/actors-jwt/grants.ts" />

Resolve the actor ID on your backend, where you still hold the admin token, then grant against that ID.

### Limits

A grant set is capped at 32 grants, 5 operations per grant, and 2048 bytes once encoded. Exceeding any of these fails issuance with `invalid JWT grant set`.

## Expiration and Renewal

Expiry is enforced mid-flight, not just at connection time. When a token's `exp` passes, the control plane cancels in-flight requests and closes open WebSockets with code `1008` and `auth.token_expired`.

With `getToken` wired up this is invisible. RivetKit catches the close, calls `getToken({ forceRefresh: true })`, and reconnects. With a static `token` the connection simply dies and does not come back, so **always use `getToken` for connections that outlive the token**.

RivetKit also reads `exp` out of the token locally and refreshes about five seconds early. That is only a cache hint to avoid a guaranteed-stale request. The control plane still verifies every token it receives.

Keep durations short. There is no revocation, so a leaked token is valid until it expires, and a 15 minute token with automatic renewal is safer than a 24 hour one.

## Inspecting a Token

To see what a token actually carries, call `GET /auth/tokens/inspect` with the token itself:

```sh
curl -H "Authorization: Bearer $TOKEN" "$RIVET_ENDPOINT/auth/tokens/inspect"
```

```json
{
  "namespace_id": "...",
  "subject": "user_alice",
  "grants": [
    { "resource": "actor_gateway", "target": { "id": "<actor-id>" }, "operations": ["read"] }
  ],
  "issued_ts": 1758700000000,
  "expires_ts": 1758700900000
}
```

## Errors

| Error | Status | Cause |
| --- | --- | --- |
| `auth.invalid_token` | 401 | Malformed, unsigned, or signed by a key this cluster does not know. |
| `auth.token_expired` | 401 | Past `exp`. Refresh and retry. |
| `auth.insufficient_permissions` | 403 | Valid token, but no grant covers this resource, target, and operation. |
| `auth.verification_unavailable` | 503 | Verification keys are temporarily unreachable. Retry. |
| `auth.issuance_unavailable` | 503 | The signing service is temporarily unreachable. Retry. |
| `auth.issuance_disabled` | 400 | `auth.jwt.issuance_enabled` is off, so `/auth/tokens` will not mint. |

Over HTTP the code arrives in the JSON body and, through the gateway, in the `x-rivet-error` response header. On a WebSocket it arrives in the close reason.

## Configuration

JWT issuance and verification are on by default when a self-hosted control plane has an admin token configured. The defaults suit most deployments.

| Setting | Default | Description |
| --- | --- | --- |
| `auth.jwt.enabled` | `true` | Verification, issuance, and key maintenance. |
| `auth.jwt.issuance_enabled` | `true` | Pauses minting without rejecting tokens already in the wild. |
| `auth.jwt.audience` | `rivet-api` | Expected `aud` claim. |
| `auth.jwt.default_duration` | `3600` | Lifetime when a request omits `duration`. |
| `auth.jwt.max_duration` | `86400` | Ceiling on `duration`. The protocol caps this at one day. |

Tokens are signed with `EdDSA` and carry `typ: rivet-auth+jwt`. The issuer is derived from the leader datacenter's public URL. Signing keys rotate every seven days on their own, with a publication window so verifiers pick up the next key before it goes live. No operator action is required.

## Not Your Application's JWTs

This page is about credentials Rivet itself issues and verifies. If you already have tokens from Clerk, Auth0, Supabase, or your own issuer, Rivet never sees them. Pass them as connection parameters and verify them inside the actor. See [Permissions](/actors/docs/permissions).

The two compose well: a Rivet JWT decides which actor a client may reach, and your own token decides who the user is once they are there.
