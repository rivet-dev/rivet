A chat room needs three things: one place that orders every message in the room, history that survives restarts, and instant delivery to everyone who is connected. A single Rivet Actor per room gives you all three.

What we'll build:

- A `chatRoom` Actor per room, keyed by the room name, that every client in the room connects to.
- Message history in the Actor's SQLite database, so it survives sleep and restarts.
- A `newMessage` event that the Actor broadcasts to every connected client on each send.
- A React client that loads the history once and then appends messages as they arrive.

<Step title="Create the chat room Actor">

Each room is its own `chatRoom` Actor. It stores the room's messages in its own [SQLite](/actors/docs/sqlite) database:

<CodeSnippet file="examples/chat-room/src/index.ts" title="index.ts" highlight="history,registry" />

- The client picks the room with the [key](/actors/docs/keys) `[roomId]`. Every client with the same room name reaches the same Actor, and different rooms never share history or connections. Rooms also spread across the cluster on their own, so a busy room does not slow down the others.
- `db({ onMigrate })` creates the `messages` table. `onMigrate` runs every time the Actor starts, which is why the statement uses `CREATE TABLE IF NOT EXISTS`.
- Every `sendMessage` for a room runs in the same Actor, the only writer to that room's database. The `AUTOINCREMENT` id therefore gives the room one order without any locks.
- `getHistory` returns every message sorted by `id`, not by `timestamp`, so every client loads the history in that order.
- `setup({ use: { chatRoom } })` registers the Actor, and `registry.start()` serves it on port 6420.

<Note>
SQLite fits history that is large, long-lived, or needs caps, pagination, or search. If you only keep a small recent window, such as the last 50 to 100 messages, you can push messages onto an array in [state](/actors/docs/state) instead and trim it to the cap on every send. That is simpler, but the whole history lives in memory and there is no query layer.
</Note>

<Warning>
`getHistory` returns every row in one response with no limit, and the table grows forever. A long-lived room eventually hits the outgoing message size and storage [limits](/actors/docs/limits). In production, add a `LIMIT` with pagination, and prune or archive old rows.
</Warning>

</Step>

<Step title="Broadcast new messages">

`sendMessage` saves the message, then pushes it to everyone in the room:

<CodeSnippet file="examples/chat-room/src/index.ts" title="index.ts" highlight="broadcast" />

- `events` declares `newMessage` as a typed [event](/actors/docs/events) carrying a `Message`. The React client gets the same payload type through `typeof registry`.
- The [action](/actors/docs/actions) sets `timestamp` with `Date.now()` on the server and lets SQLite assign the `id`. Never accept timestamps or ids from the client.
- The insert uses `?` placeholders, so user text never ends up inside the SQL string. Keep every query parameterized.
- The insert finishes before `c.broadcast("newMessage", message)`, so a message that other clients have seen is already saved. The broadcast reaches every connection in the room, including the sender, and the action also returns the message to the caller.
- `c.broadcast` is for messages the whole room should see. For private payloads, such as a direct message inside a room, send to a single connection with `conn.send` instead.

<Warning>
The example has no authentication. Any client can join any room by knowing its name, and `sender` is a plain action argument, so anyone can post as anyone. In production, check a token in [`onBeforeConnect`](/actors/docs/permissions), keep the user's identity in [connection state](/actors/docs/connections#connection-state), check room membership before serving history, and read the sender from the connection instead of the arguments.
</Warning>

<Warning>
`sendMessage` accepts empty text and text of any length, and any client can call it as often as it likes. Every call is saved and sent to every connection, so one spammer costs the whole room. In production, trim the text on the server, reject empty messages, cap the length, and rate limit each connection.
</Warning>

</Step>

<Step title="Connect the React client">

The React client connects with `useActor`, loads the history once, then appends every `newMessage`:

<CodeSnippet file="examples/chat-room/frontend/App.tsx" title="App.tsx" region="client" highlight="connect,events,send" />

- `createRivetKit<typeof registry>` returns hooks typed against the backend, so action arguments and event payloads are checked. See the [React client](/actors/docs/clients/react).
- `useActor({ name: "chatRoom", key: [roomId] })` connects to the room's Actor and creates it if it does not exist yet. The room input defaults to `general`. Changing it connects to a different Actor with its own history.
- Once `chatRoom.connection` is ready, the client calls `getHistory` once to render the backlog. After that, `useEvent("newMessage", ...)` appends each new message as it arrives.
- The sender sees its own message through the same broadcast as everyone else, so there is only one code path for rendering messages. `sendMessage` only waits for the action and clears the input.

</Step>

## Extend it

- **Typing indicators and presence**: keep the username and a typing flag in [connection state](/actors/docs/connections#connection-state), never in SQLite, so they disappear with the connection. Broadcast a typing event only when a user starts or stops typing, broadcast join and leave from `onConnect` and `onDisconnect`, and clear a typing indicator on the client after a short timeout so a dropped connection never leaves it stuck.
- **Per-user inbox**: for offline delivery, unread counts, or notifications, add a `userInbox` Actor keyed by user id. The room forwards each message to every member's inbox with [actor-to-actor calls](/actors/docs/communicating-between-actors), and the inbox keeps the unread state. A direct message can be a `chatRoom` keyed by the sorted pair of user ids.
