The usual way to build a multi-tenant app is one shared database with a `tenant_id` column on every table, and every query has to remember to filter on it. With Rivet Actors you can give each tenant a database of its own instead.

What we'll build:

- A `companyDatabase` Actor per tenant, keyed by the company name, that owns all of that tenant's data.
- A SQLite database inside each Actor, with `employees` and `projects` tables and a migration that runs per tenant.
- Actions that read and write the tables with SQL, and events that push every new row to the tenant's open dashboards.
- A React dashboard that switches tenants by switching the Actor key.

<Steps>

<Step title="Install">

```sh
npm add rivetkit@next @rivetkit/react@next
```

</Step>

<Step title="Create the tenant Actor">

Each tenant is its own `companyDatabase` Actor:

<CodeSnippet file="examples/per-tenant-database/src/index.ts" title="index.ts" highlight="actor,registry" />

- The [key](/actors/docs/keys) is the tenant id. `companyDatabase["Acme"]` always reaches the same Actor, and two tenants can never share one. Reaching another tenant's data means building the wrong key, not forgetting a `WHERE` clause.
- Keys are arrays, so the tenant id is passed as `[tenantId]` and never concatenated into a string such as `"tenant:" + tenantId`. There is nothing to escape.
- `onCreate` runs once, the first time a tenant's Actor is created, after the tables exist. It reads the tenant id from `c.key[0]` and inserts the single `company` row that tracks when the tenant's database was created and last updated. See [Lifecycle](/actors/docs/lifecycle).
- `setup({ use: { companyDatabase } })` registers the Actor, and `registry.start()` serves it on port 6420.

</Step>

<Step title="Define the schema and migration">

`db({ onMigrate })` gives every `companyDatabase` Actor its own [SQLite](/actors/docs/sqlite) database and creates the tables in it:

<CodeSnippet file="examples/per-tenant-database/src/index.ts" title="index.ts" highlight="schema" />

- The database belongs to the Actor, and the Actor belongs to the tenant, so every tenant has its own tables. No table has a `tenant_id` column.
- `onMigrate` runs every time the Actor starts, before it serves any action, so every statement uses `CREATE TABLE IF NOT EXISTS`. RivetKit wraps it in a savepoint: if it throws, all of its SQL rolls back and the Actor does not start.
- Migrations run per tenant. Each tenant's database is migrated when its Actor next starts, instead of one large migration against a shared database. To change the schema later, add steps that are safe to run again, or use numbered migrations as shown in [Versions](/docs/versions#sqlite-recommended-for-complex-schemas).
- The schema enforces its own rules. `company` can only hold the row with `id = 1`, and `projects.status` must be `planning`, `active`, or `done`.

<Note>
SQLite fits tenant data that is relational, grows over time, or needs queries. For a small dataset per tenant that always fits in memory, plain [state](/actors/docs/state) is simpler: the same one Actor per tenant model works, but there are no tables or queries. If you want a typed schema and generated migration files, use [SQLite with Drizzle](/actors/docs/sqlite-drizzle) on the same database.
</Note>

</Step>

<Step title="Read and write with SQL">

The actions are plain SQL against the tenant's tables:

<CodeSnippet file="examples/per-tenant-database/src/index.ts" title="index.ts" highlight="read,write" />

- `c.db.execute<Employee>(...)` returns the rows as an array of `Employee` objects, ordered by `id`. `getStats` counts both tables with subqueries and reads the timestamps from the `company` row.
- Every query uses `?` placeholders, so names and roles from the client never end up inside the SQL string.
- Each write runs inside `c.db.transaction`. The `INSERT ... RETURNING` and the `UPDATE` of `company.updated_at` either both happen or neither does. A project with an unknown status fails the `CHECK` constraint, the transaction rolls back, and the caller gets an error. The static `name` groups the transaction in [SQLite profiling](/actors/docs/sqlite-profiling).
- The Actor is the only writer to its tenant's database, so the writes need no locks, and `AUTOINCREMENT` gives each tenant its own id sequence.
- Queries only ever see one tenant. A query across tenants, such as an admin report, needs a separate path: call each tenant's Actor with [actor-to-actor calls](/actors/docs/communicating-between-actors), or copy the rows you need into a shared analytics store.

<Warning>
`listEmployees` and `listProjects` return every row with no limit, and the actions only trim their input. In production, add `LIMIT` with pagination, cap the length of names and roles, and check each caller's role before `addEmployee` and `addProject`, not only when they connect. See [Permissions](/actors/docs/permissions).
</Warning>

</Step>

<Step title="Broadcast changes">

After each write commits, the Actor pushes the new row to every dashboard that has the tenant open:

<CodeSnippet file="examples/per-tenant-database/src/index.ts" title="index.ts" highlight="broadcast" />

- `events` declares `employeeAdded` and `projectAdded` as typed [events](/actors/docs/events) carrying the same `Employee` and `Project` rows the list actions return.
- `c.broadcast` runs after the transaction has committed, so a row other clients have seen is already saved. The action also returns the row to the caller.
- A broadcast only reaches the connections of this tenant's Actor. Dashboards open on another company never receive it.

</Step>

<Step title="Connect the dashboard">

The React dashboard connects to the Actor for the signed-in company, loads its data, then applies events as they arrive:

<CodeSnippet file="examples/per-tenant-database/frontend/App.tsx" title="App.tsx" region="client" highlight="connect,events,add" />

- `createRivetKit<typeof registry>` returns hooks typed against the backend. See the [React client](/actors/docs/clients/react).
- `useActor({ name: "companyDatabase", key: [companyName] })` connects to that company's Actor and creates it, with its database, if it does not exist yet. Switching companies connects to a different Actor, so the whole dataset swaps.
- Once `company.connection` is ready, the dashboard calls `listEmployees`, `listProjects`, and `getStats` together. After that, `useEvent` appends each new row and refreshes the stats.
- `addEmployee` and `addProject` only wait for the action. The new row shows up through the same event that every other open dashboard receives.

<Warning>
In the example, the visitor types a company name and that string becomes the Actor key, so anyone can read and write any tenant's data. In production, the tenant id must come from your auth, never from the client:

- Derive the tenant id from a verified credential, such as a claim in a [JWT](/docs/jwt).
- In [`onBeforeConnect`](/actors/docs/permissions) or `createConnState`, check that the credential's tenant matches `c.key[0]` and reject the connection if it does not. Keep the verified user in [connection state](/actors/docs/connections#connection-state) for per-action checks.
- Never build a key from one tenant's input to reach another tenant's Actor.
</Warning>

</Step>

<Step title="Try it">

```sh
git clone https://github.com/rivet-dev/rivet.git
cd rivet/examples/per-tenant-database
pnpm install
pnpm dev
```

Open `http://localhost:5173`, continue as one company, and add a few employees and projects. Switch to another company name and the dashboard is empty, because that company has its own Actor and its own database. Open the same company in a second window, add an employee in one, and it appears in both.

`pnpm test` runs [the example's test](https://github.com/rivet-dev/rivet/tree/main/examples/per-tenant-database/tests/per-tenant-database.test.ts), which writes to `companyDatabase["Alpha Co"]` and `companyDatabase["Beta Co"]` and checks that neither sees the other's rows.

</Step>
