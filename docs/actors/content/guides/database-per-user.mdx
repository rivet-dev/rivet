### What we'll build

- A `user` Actor per user, created at sign-up and keyed by the user id from your auth provider.
- A SQLite database inside each `user` Actor that holds only that user's rows.
- API routes that look up the user id from the session and call actions on that user's Actor.
- Schema migrations in `onMigrate` that run on each user's database the next time it wakes.
- Data access with no shared table, no `user_id` filter on every query, and no row-level security policies.

### Similar tools

This is the same job as a Turso database per user, Neon branches per user, Supabase row-level security, or Cloudflare Durable Objects with SQLite. On Rivet the database lives inside the Actor that serves it, so queries run next to the data, and an idle user's Actor sleeps until the next request wakes it.
