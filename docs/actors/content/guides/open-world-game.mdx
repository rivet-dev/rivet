What we'll build:

- An `openWorldChunk` Actor per chunk, keyed by world id and chunk coordinates.
- A 10 tick per second loop in each chunk that moves its players and sends snapshots.
- Blocks that players place and remove, saved in the chunk's SQLite database.
- A browser client that watches every chunk in view and moves the player to the next chunk at an edge.

<Steps>

<Step title="Install">

```sh
npm add rivetkit
```

</Step>

<Step title="Create the chunk Actor">

Each chunk of the world is its own `openWorldChunk` Actor. A connection can watch a chunk, and becomes a player in it with `enterChunk`:

<CodeGroup>
<CodeSnippet file="examples/multiplayer-game-patterns/src/actors/open-world/chunk.ts" title="chunk.ts" highlight="chunk,membership" />
<CodeSnippet file="examples/multiplayer-game-patterns/src/actors/open-world/config.ts" title="config.ts" />
</CodeGroup>

- The key is `[worldId, chunkX, chunkY]`. `createVars` reads the coordinates from `c.key`, so a chunk knows where it is without any input. It also loads the chunk's saved blocks, players, and tick from SQLite into `c.vars`. Connections only live in memory, so restored players start without one. There is no matchmaker: whoever knows a position can compute its chunk key.
- A connection is not a player. `onConnect` records the `playerId` from the connection params with `inChunk: false`, so a client can watch a chunk without standing in it. `enterChunk` adds the player at a spawn point clamped to the chunk, and `leaveChunk` removes it. `addPlayer` and `removePlayer` do the same thing.
- After a restart, the first connection whose `playerId` matches a restored player takes that player back, so a reconnecting client keeps control where it was.
- `setInput` only accepts input from the connection that controls the player in this chunk, and clamps each axis to -1 to 1. The client sends a direction, never a position.
- Positions are local to the chunk, from 0 to `CHUNK_SIZE` (1200). The world position is `chunkX * CHUNK_SIZE + x`.

<Warning>
The client chooses its `playerId` and its spawn point, so it can claim another player's id or enter any chunk at any spot. In production, issue the player id from your [authentication](/guides/authentication), and have the old chunk hand the player to the next one instead of trusting the client's position.
</Warning>

</Step>

<Step title="Run the tick loop">

Each chunk simulates only its own players, in a background task that `onWake` launches on every start:

<CodeSnippet file="examples/multiplayer-game-patterns/src/actors/open-world/chunk.ts" title="chunk.ts" highlight="tick,snapshot,save" />

- `runChunk` ticks on `interval(TICK_MS)` until `c.aborted` is set. Every 100 ms it moves each player by `SPEED`, or 2.5 times that while sprinting, and clamps them to the chunk edges.
- `onSleep` and `onDestroy` wait for the loop to save and exit. `onDestroy` needs the wait because the Actor closes its database right after `onDestroy` returns.
- Load grows with the number of chunks in use, not the size of the world. A chunk nobody has visited has no Actor, and a chunk nobody is connected to [sleeps](/actors/docs/lifecycle#sleeping) after the idle timeout and resumes from its last save on the next connection.
- Ticks only change memory. Every `SNAPSHOT_INTERVAL_MS` (1 second), and once more when the Actor stops, `saveChunk` writes the tick and every player's name, color, and position in one `c.db.transaction`, so a crash loses at most about a second of movement. The loop removes a restored player whose client hasn't reconnected within `RECONNECT_GRACE_MS` (5 seconds).
- `broadcastSnapshot` loops over `c.conns` and calls `conn.send` instead of `c.broadcast`, because each snapshot sets `selfPlayerId` only for the connection that controls that player.
- Every snapshot holds the whole chunk: all players and all blocks. That is fine for a small chunk. For busy chunks, send a full snapshot when a client connects and only the changes after that.

<Note>
The server owns movement and clients smooth toward the positions it sends. A sandbox game can let the client move the player and send its position instead, as long as the chunk checks each update: cap the distance moved per update by elapsed time, reject teleports, keep the player inside the chunk, and limit how often a connection can send updates.
</Note>

</Step>

<Step title="Save blocks in the chunk">

Players build on a 24 by 24 grid in each chunk:

<CodeSnippet file="examples/multiplayer-game-patterns/src/actors/open-world/chunk.ts" title="chunk.ts" region="blocks" />

- Blocks are saved in the `blocks` table, one row per grid cell with the color of the player who placed it. `c.vars.blocks` keeps the same data in memory as a map from `"gridX,gridY"` to color, so snapshots never read the database. Each change updates the map and writes the row, so a chunk keeps its blocks when it sleeps and wakes. Players are not written per action: the tick loop saves them, and `onDisconnect` removes them.
- `placeBlock` only works for a player standing in this chunk and rejects cells outside the grid. `removeBlock` only checks that the caller is connected, so a client watching from the next chunk can remove blocks. Check it the same way as `placeBlock` if you don't want that.
- Both actions send a snapshot only when a block actually changed.

<Note>
Loading every block into memory works for a small grid per chunk. For bigger worlds, with many blocks or inventories, query the [SQLite](/actors/docs/sqlite) table by position instead of loading all of it on wake.
</Note>

</Step>

<Step title="Connect players">

The client opens one connection per chunk in view, with the same `playerId` on each:

<CodeSnippet file="examples/multiplayer-game-patterns/frontend/games/open-world/open-world-game.ts" title="open-world-game.ts" highlight="connect,neighbors" />

- `connectToChunk` calls `getOrCreate([WORLD_ID, String(cx), String(cy)])`, which creates the chunk on first use. The shared `playerId` lets each chunk match the connection to its player.
- `updateAdjacentChunks` keeps a connection open to every chunk the camera can see and disposes the rest. Zooming out opens more. This is the interest management: a client only gets snapshots from chunks it is connected to.
- Snapshots only set target positions. The `requestAnimationFrame` draw loop moves each player 20% (`LERP_FACTOR`) toward its target every frame, outside React state.

When the player walks into an edge, the client moves them to the next chunk:

<CodeSnippet file="examples/multiplayer-game-patterns/frontend/games/open-world/open-world-game.ts" title="open-world-game.ts" highlight="primary,transfer" />

- The snapshot handler calls `initiateTransfer` when the player is at an edge and still pushing toward it. It converts to world coordinates, steps one unit past the edge, and resolves the new chunk key.
- `setPrimaryChunk` calls `enterChunk` on the new chunk and waits up to 1.5 seconds for a snapshot whose `selfPlayerId` is this player. Only then does it call `leaveChunk` on the old chunk, so the player is never missing from both. If the wait times out, it leaves the new chunk and stays where it was.
- Input is stored per chunk, so it sends the current direction to the new chunk right away.

</Step>

<Step title="Try it">

Run the example:

```sh
git clone https://github.com/rivet-dev/rivet.git
cd rivet/examples/multiplayer-game-patterns
pnpm install
pnpm dev
```

Open `http://localhost:5173`, choose **Open World**, and click **Enter World**. Move with WASD, sprint with Shift, and zoom with + and -. Left click places a block and right click removes it. Walk past a chunk edge and the HUD at the top switches to the new chunk, while the list on the right shows every chunk you are connected to. Click **Add Bot**, or open a second tab, to see other players in nearby chunks.

</Step>
