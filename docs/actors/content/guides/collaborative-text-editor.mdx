What we'll build:

- A `document` Actor per document that keeps the merged Yjs document and relays every edit to the other editors.
- Live cursors and names over the Yjs Awareness protocol, cleaned up when someone closes the tab.
- A snapshot of the document in the Actor's KV storage, so it survives restarts.
- A `documentList` Actor per workspace that creates documents and lists them.
- A React editor that syncs a local `Y.Doc` with the Actor.

<Note>
This guide uses a CRDT. Yjs merges edits in any order on any client, so the server only relays and stores updates and never has to understand them. The other approach is operational transformation (OT), where one server orders and rewrites every operation. It suits editors that need a single authoritative order, but the server has to implement a transform for every operation type and long offline sessions are hard to merge. See [Collaborative Text Editor (OT)](/guides/collaborative-text-editor-ot).
</Note>

<Step title="Create the document Actor">

Each document is its own `document` Actor, keyed by `[workspaceId, documentId]`:

<CodeSnippet file="examples/collaborative-document/src/index.ts" title="index.ts" region="document" />

- `createState` holds only metadata: `title`, `createdAt`, and `updatedAt`. It reads the title from the creation [input](/actors/docs/input) that `documentList` passes in.
- The live `Y.Doc` and its `Awareness` live in [vars](/actors/docs/state#ephemeral-state), because they are class instances that cannot be saved as JSON state. `createVars` rebuilds them every time the Actor starts by loading the binary `yjs:doc` key from [KV storage](/actors/docs/kv).
- `connState` gives every connection its own list of awareness client ids, which is used to clean up presence on disconnect.
- The multi-part [key](/actors/docs/keys) scopes the document to its workspace, so two workspaces can never reach each other's documents by id.

</Step>

<Step title="Relay Yjs updates">

Clients sync through one action and one event:

<CodeSnippet file="examples/collaborative-document/src/index.ts" title="index.ts" region="relay" highlight="sync" />

- `getContent` returns the whole merged document as one Yjs update. A client calls it once on connect to catch up.
- `applyUpdate(update, "sync")` applies a client's change to the server's `Y.Doc` with origin `"client"` and broadcasts the same small update as the `sync` [event](/actors/docs/events). The server never transforms or orders edits. Yjs merges are commutative, so every client ends up with the same text no matter which update arrives first.
- Updates cross the action boundary as `number[]`, because action arguments are serialized. `toBytes` and `toNumbers` convert them back and forth on both sides.
- The broadcast reaches the sender too. The client applies it with origin `"remote"`, which Yjs ignores because it already has the change, and the client's listener skips `"remote"` updates, so nothing is sent twice.

<Warning>
`applyUpdate` accepts any `number[]` of any size, and the example client sends one action per keystroke. In production, cap the payload size, rate limit each connection, and batch edits on the client.
</Warning>

</Step>

<Step title="Share presence">

Names, colors, and cursor positions travel over the Yjs Awareness protocol, through the same action with kind `"awareness"`:

<CodeSnippet file="examples/collaborative-document/src/index.ts" title="index.ts" region="presence" highlight="disconnect,awareness" />

- `applyUpdate(update, "awareness", clientId)` applies the change to the server's `Awareness`, remembers `clientId` in that connection's `connState`, and broadcasts the `awareness` event. Presence is never saved.
- `getAwareness` returns everyone's current presence, so a client that joins late sees the other cursors right away.
- `onDisconnect` removes every awareness client the connection asserted and broadcasts the removal, so the cursor disappears even if the tab closed without saying goodbye. See [Connections](/actors/docs/connections).

<Warning>
The `clientId` comes from the client and is trusted as is, so one connection could remove another user's cursor by claiming its id. In production, check it against state the server owns for that connection.
</Warning>

</Step>

<Step title="Persist snapshots">

Every `"sync"` update also saves the whole document:

<CodeSnippet file="examples/collaborative-document/src/index.ts" title="index.ts" region="sync" highlight="persist" />

- `Y.encodeStateAsUpdate` encodes the merged document as one compact update, and `c.kv.put` overwrites the single `yjs:doc` key with it. There is no update log, so there is nothing to replay on start and no separate compaction job. Encoding the merged state is the compaction.
- The write finishes before the broadcast, so an edit that other clients have seen is already saved. If the Actor crashes or moves, `createVars` loads the last snapshot.
- Every keystroke rewrites the whole document. That is simple and fine for small and medium documents.

<Warning>
A single KV value is limited to 128 KiB (see [Limits](/actors/docs/limits)). Once the encoded document grows past that, `kv.put` throws, so `applyUpdate` fails before the broadcast and edits are neither saved nor relayed.
</Warning>

<Note>
For large documents or high edit rates, append each incremental update to an update log under its own key and write a merged snapshot only every N updates, then delete the log entries it covers. Start then loads the snapshot and replays the log. Only switch once the full-snapshot write is the measured bottleneck or the document nears the value limit.
</Note>

</Step>

<Step title="Index documents per workspace">

A `documentList` Actor per workspace creates documents and lists them. The registry starts both Actors:

<CodeSnippet file="examples/collaborative-document/src/index.ts" title="index.ts" region="list" />

- This is the coordinator pattern from [Design Patterns](/actors/docs/design-patterns): `documentList` owns discovery, and each `document` Actor owns one document's realtime state.
- `createDocument` creates the `document` Actor explicitly with `c.client<typeof registry>()` and passes `{ title, createdAt }` as input. See [Communicating Between Actors](/actors/docs/communicating-between-actors).
- `deleteDocument` only removes the entry from the list. The `document` Actor and its snapshot stay behind. To delete a document for real, also [destroy](/actors/docs/destroy) the Actor.

<Warning>
The example has no authentication. Anyone who knows a workspace id can list and open its documents, and connecting with a new workspace id creates an empty `documentList`. In production, authenticate connections and check that the user may open each `[workspaceId, documentId]`. See [Authentication](/guides/authentication) and [Permissions](/actors/docs/permissions).
</Warning>

</Step>

<Step title="Connect the editor">

Each open document creates its own `Y.Doc` in the browser and sends every local change to the Actor:

<CodeSnippet file="examples/collaborative-document/frontend/App.tsx" title="App.tsx" region="send" />

Then, every time the connection opens, it catches up and listens for changes from others:

<CodeSnippet file="examples/collaborative-document/frontend/App.tsx" title="App.tsx" region="connect" />

- `useActor({ name: "document", key: [workspaceId, document.id] })` connects to the document's Actor. The text lives in `doc.getText("content")`.
- Typing calls `doc.transact(..., "local")`, which fires `handleDocUpdate`, which sends the update with `applyUpdate`. Changes from the Actor are applied with origin `"remote"`, so they update the screen but are not sent back.
- On connect and reconnect, the client applies `getContent` and `getAwareness` before the `sync` and `awareness` events take over. The awareness listener sends local cursor moves the same way as edits.
- Edits made while the connection is down stay in the local `Y.Doc` and are not sent on reconnect. To keep them, send `Y.encodeStateAsUpdate(doc)` after the catch-up, and Yjs merges whatever the Actor is missing.

<Note>
The example edits a plain `<textarea>` and replaces the whole text on every change, so two people typing at the same moment can end up with both versions of the text. A real editor should use a Yjs binding that applies small edits, such as y-prosemirror, y-codemirror, or y-monaco. The Actor does not change.
</Note>

</Step>

<Step title="Try it">

```sh
git clone https://github.com/rivet-dev/rivet.git
cd rivet/examples/collaborative-document
pnpm install
pnpm dev
```

Open `http://localhost:5173` in two tabs and change the **Name** in one of them. Click **Create** in the first tab to make a document. The list does not update live, so reload the second tab and click **Open** on the new document. Type in either tab and the text shows up in both, with the other person's cursor marked by their name and listed under **Active collaborators**.

</Step>
