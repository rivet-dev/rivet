Rivet Actor schedules are durable timers that live with the Actor. They survive sleep, restarts, upgrades, deploys, and crashes, so you do not need a separate cron service or a job queue to run work on time.

This guide adds a daily report to a reminders app. A `reminderActor` stores reminders that fire once, and a cron job on the same Actor sums them up every morning.

What we'll build:

- A `reminderActor` per key that stores reminders and the last daily report in its state.
- A `daily-report` cron job, installed when the Actor is created, that runs every day at 9:00 Los Angeles time.
- A `sendDailyReport` action that the job calls to build the report, save it, and broadcast it to connected clients.
- One-shot reminders scheduled with `c.schedule.after` and `c.schedule.at`, and cancelled with `c.schedule.cancel`.

<Step title="Create the reminder Actor">

The Actor's state holds the reminders and the bookkeeping the daily report needs:

<CodeSnippet file="examples/scheduling/src/index.ts" title="index.ts" highlight="state,registry" />

- `reminders` and `completedCount` belong to the one-shot reminders you add in the last step. `lastReportAt` and `lastReport` belong to the daily report. All of it is [state](/actors/docs/state), saved automatically.
- `lastReportAt` starts at `0`, so the first report covers everything that happened before it.
- `events` declares `reminderTriggered` and `dailyReport`, the two typed [events](/actors/docs/events) the Actor broadcasts.
- Every schedule belongs to one Actor, so the [key](/actors/docs/keys) decides the scope of the job. The example uses a single key, `["main"]`, which gives one global job. Use one key per user or per resource for reminders, trials, billing periods, and other per-entity jobs.

</Step>

<Step title="Install the daily job">

`onCreate` installs the cron job the first time the Actor is created:

<CodeSnippet file="examples/scheduling/src/index.ts" title="index.ts" highlight="install" />

- `c.cron.set` stores a named recurring job on the Actor. `0 9 * * *` is a standard five-field cron expression for 9:00 every day.
- `timezone` takes an IANA name and defaults to UTC. The job keeps firing at 9:00 local time across daylight saving changes.
- `action` names an action on the same Actor. The name is fixed in your code, never taken from a client.
- `name` is unique per Actor. Calling `cron.set` again with the same name updates the job instead of adding a second one, so there is no need to re-arm a one-shot schedule after every run.
- The Actor does not stay awake between runs. It can [sleep](/actors/docs/lifecycle#sleeping) as usual, and Rivet wakes it when the job is due.

<Note>
`onCreate` runs once per Actor, so a new expression in your code only reaches Actors created after the deploy. To update Actors that already exist, call the same `cron.set` from `onWake`, which runs on every start. Calling it with an unchanged expression keeps the next run time as it is.
</Note>

</Step>

<Step title="Build the report">

The cron job calls `sendDailyReport`, an ordinary action:

<CodeSnippet file="examples/scheduling/src/index.ts" title="index.ts" highlight="report" />

- When a schedule calls an action, it appends a `ScheduledFireInfo` object after the action's own arguments. It carries `kind`, `id`, `name`, `scheduledAt`, and `firedAt`.
- The report covers the window from `lastReportAt` to `fire.scheduledAt`. Using the planned time instead of `Date.now()` keeps every window exactly one day long, even when a run starts a little late.
- If the window was already reported, the action returns the saved report and changes nothing. Running it twice for the same occurrence is harmless, so a manual retry is safe.
- It saves the report to `c.state.lastReport` and broadcasts `dailyReport`, so connected clients see it right away.
- A run that is still going when the next one is due makes the next one skip. Failed runs are not retried; the job continues at its next normal time. See [Execution behavior](/actors/docs/schedule#execution-behavior).

<Warning>
`sendDailyReport` is a public action, so any client that can reach the Actor can call it with any arguments. In production, check who connects with `onBeforeConnect` (see [Authentication](/guides/authentication)) and keep scheduled actions idempotent like this one.
</Warning>

<Warning>
Renaming or removing `sendDailyReport` deletes the `daily-report` job the next time it is due, because a recurring job is removed when its action no longer exists. Rename the action and the `action` field of `cron.set` in the same deploy, and call `cron.set` from `onWake` so existing Actors pick up the new name.
</Warning>

</Step>

<Step title="Check on the job">

`getDailyReport` returns the last report, the job's next run time, and its recent runs:

<CodeSnippet file="examples/scheduling/src/index.ts" title="index.ts" highlight="read" />

- `c.cron.get` returns the job's settings and `nextRunAt`, the Unix time in milliseconds of the next run.
- `c.cron.history` returns recent runs, newest first. Each entry has a `result` of `running`, `ok`, `error`, or `skipped`, plus the error when a run failed. Since failed runs are not retried, this is where you find them and build your own retry if you need one.
- A job keeps 100 history entries by default. Pass `maxHistory` to `cron.set` to keep up to 1,000, or `0` to turn history off.

</Step>

<Step title="Add one-shot jobs, intervals, and cancellation">

The reminders are one-shot schedules. Each one calls `triggerReminder` once and keeps the schedule ID so it can be cancelled:

<CodeSnippet file="examples/scheduling/src/index.ts" title="index.ts" highlight="one-shot,cancel" />

- `scheduleReminder` uses `c.schedule.after` with a delay in milliseconds. `scheduleReminderAt` uses `c.schedule.at` with a Unix timestamp in milliseconds.
- Both return a schedule ID, which the reminder stores as `scheduleId`. `cancelReminder` passes it to `c.schedule.cancel`, which returns `false` if the reminder already fired.
- Like the cron job, the target action name `triggerReminder` is fixed in code, and the reminder ID is passed as its argument.

Pick the API by how often the work runs:

| API | Use it for |
| --- | --- |
| `c.schedule.after(delayMs, action, ...args)` | Run once after a delay. Returns an ID for `c.schedule.cancel`. |
| `c.schedule.at(timestamp, action, ...args)` | Run once at a Unix timestamp in milliseconds. Returns an ID for `c.schedule.cancel`. |
| `c.cron.set({ name, expression, action })` | Run on a calendar schedule, in a timezone. |
| `c.cron.every({ name, interval, action })` | Run every `interval` milliseconds, at least 5,000. Use it for frequent work such as presence sweeps or cache refreshes. Runs stay on their planned times, so a slow run does not push the next one later. |
| `c.cron.delete(name)` | Stop a recurring job. Recurring jobs are managed by name, and calling `cron.set` or `cron.every` again with the same name replaces the job. |

See [Schedule & Cron](/actors/docs/schedule) for `c.schedule.list`, `c.cron.list`, and the full set of options.

</Step>
