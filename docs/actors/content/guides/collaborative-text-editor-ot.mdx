### What we'll build

- A `document` Actor per document that is the single sequencer for its edits.
- Clients that send each operation with the revision it was based on, and keep sending later edits only after the last one is acknowledged.
- A transform step that rewrites an incoming operation against every operation committed since its revision, then assigns it the next revision.
- An operation log in the Actor's SQLite database, with periodic snapshots so late joiners and restarts do not replay the whole history.
- A browser client that applies transformed operations from other editors and rebases its own pending edits on top.

### Similar tools

This is the same job as ShareDB, Google Docs-style OT servers, Firepad, or Liveblocks. On Rivet each document is an Actor, so one place orders every edit for that document without a separate database lock, and the Actor sleeps when nobody has it open. For the CRDT approach, where the server only relays and stores updates, see [Collaborative Text Editor (CRDT)](/guides/collaborative-text-editor).
