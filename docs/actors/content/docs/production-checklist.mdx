Deploy-time configuration (environment variables, node pools and graceful
shutdown) lives in the
[self-host production checklist](/docs/deploy/self-host/workers/production-checklist/).
This page covers application design: what to get right before writing the
actor, not before shipping it.

## Actors

### Design Patterns

- **Do not use god actors.** Avoid putting all logic into a single actor type. See [Design Patterns](/actors/docs/design-patterns).
- **Do not use actor-per-request patterns.** Avoid creating a new actor for each request. See [Design Patterns](/actors/docs/design-patterns).

### Lifecycle

- **Do not rely on `onSleep` for critical cleanup.** `onSleep` is not called during crashes or forced terminations. See [Lifecycle](/actors/docs/lifecycle).

### State

- **Verify `c.vars` does not grow unbounded.** Load only what you need into memory. Use [SQLite](/actors/docs/sqlite) for unbounded or append-heavy data instead.
- **Use input parameters and `onCreate` for actor initialization.** See [Input Parameters](/actors/docs/input).

### Events

- **Use `conn.send()` instead of `c.broadcast()` for private events.** `c.broadcast()` sends to all connected clients. Use `conn.send()` to send events to a specific connection. See [Realtime](/actors/docs/events).

### Actions

- **Review action timeout configuration.** The default `actionTimeout` is 60 seconds. Increase it if you have long-running actions like API calls or file processing. See [Actor Configuration](/actors/docs/actor-configuration).
- **Review message size limits.** The default `maxIncomingMessageSize` is 64 KiB and `maxOutgoingMessageSize` is 1 MiB. Increase if your actors send or receive large JSON payloads. See [Registry Configuration](/actors/docs/registry-configuration).

### Workflows

- **Verify workflows do not generate infinite steps.** Use `ctx.loop` to avoid creating unbounded step histories. See [Workflows](/workflows/docs).

## Security

### Authentication

- **Validate connections in `onBeforeConnect`.** Do not trust client input without validation. See [Permissions](/actors/docs/permissions).

### CORS

- **Configure CORS for production.** Restrict allowed origins instead of allowing all. See [CORS](/actors/docs/cors).

### Tokens

- **Keep your Rivet token server-side.** Put it in `RIVET_ENDPOINT` only. Never expose it in client-side code, public repositories, or browser environments.
- **Give browser clients scoped tokens.** Issue [scoped tokens](/docs/jwt) from your backend. See [Endpoints](/docs/connect).

### Access Control

Access control is only needed if you want granular permissions for different clients. For most use cases, basic authentication in `onBeforeConnect` is sufficient.

- **Use deny-by-default rules.** Reject unknown roles in `onBeforeConnect`, action handlers, and `canSubscribe`. See [Permissions](/actors/docs/permissions).
- **Authorize actions explicitly.** Check the caller's role in each action handler and throw `forbidden` for unauthorized access.
- **Gate event subscriptions.** Use `canSubscribe` hooks to restrict which clients can subscribe to events.

## Clients

- **Dispose connections and/or client when not in use (JavaScript client).** Call `conn.dispose()` or `client.dispose()` when no longer needed to free resources. React and SwiftUI clients handle this automatically. See [Connection Lifecycle](/actors/docs/clients/javascript#connection-lifecycle).

## Upgrades

- **Upgrade a self-hosted control plane before RivetKit.** See [Upgrading RivetKit](/docs/versions#upgrading-rivetkit).
