---
title: "Forking"
description: "Fork a Rivet Actor into a new actor that starts with the source's SQLite database without copying it, then runs on its own."
skill: true
---

A fork is a new Rivet Actor that starts with everything another actor had saved: its SQLite database, its schedules, and its workflow progress. The fork gets its own ID and key, starts as soon as it is created, and then runs on its own. Writes to the fork never reach the source, and writes to the source never reach the fork. Use forks to branch an agent's conversation, fan work out to copies that share the same context, or duplicate a document.

**Forks are copy-on-write: a fork shares the source's data instead of copying it, and stores only what it writes afterwards.**

## Forking from a client

Call `client.<actor>.fork` with the source actor's ID. It returns a handle to the new actor once its copy is ready:

<CodeSnippet file="examples/docs/actors-forking/from-client.ts" title="client.ts" />

| Option | Description |
| --- | --- |
| `key` | The new actor's key. Omit it for a keyless actor. |
| `input` | Any CBOR-compatible value. It reaches the new actor's `onFork` as `fork.input`. |
| `params`, `signal` | Connection parameters for the returned handle, and a signal that aborts the call. |

- Call `fork` on the accessor for the source's actor type, since a fork always has the source's name and node pool.
- The fork holds every write the source had saved when the call arrived. Writes the source has not saved yet, such as a transaction that is still open or anything in `c.vars`, are not in it.
- A fork is not idempotent: each call makes a new actor, and a `key` that is already taken fails with `actor.duplicate_key`. Give forks a key when a retry must never make a second copy.

## onFork

`onFork(c, fork)` runs once, at the first start of a fork, after `onMigrate` and `createVars` and before `onWake`. `createState` and `onCreate` do not run for a fork.

| Field | Description |
| --- | --- |
| `fork.actorId` | The source actor's ID. |
| `fork.key` | The source actor's key, as an array. |
| `fork.forkedAt` | When the fork was made, in milliseconds since the epoch. |
| `fork.input` | The `input` passed to `fork`, or `undefined`. It comes from the caller. |

Use it to cancel the schedules and cron jobs the fork copied, to drop or replace resources that belong to the source, and to record the fork input:

## Fork chain

`c.forkChain` lists every fork behind an actor, oldest first, each with `actorId`, `key`, and `forkedAt`. It is empty for an actor that was never forked, and `c.forkChain.at(-1)` is the actor this one was forked from. Namespace forks are not listed.

## Permissions

A token needs two grants to fork an actor:

- `fork` on the source actor, by its ID or `"any"`, because the fork copies the source's data.
- `create` on `"any"` actor, because the fork is a new actor whose ID is not known before the fork.

No other operation allows a fork: a token that can read, create, or connect to an actor cannot fork it. Issue one from your backend with `client.auth.issueToken`:

```ts token.ts @nocheck
import { createClient } from "rivetkit/client";
import type { registry } from "./index";

// Runs on your backend. The endpoint carries your Rivet token.
const client = createClient<typeof registry>();

// A token that can fork doc-1 into new actors, and nothing else.
const sourceId = await client.document.getOrCreate(["doc-1"]).resolve();
const { token, expiresAt } = await client.auth.issueToken({
	subject: "user-123",
	expiresIn: 900,
	grants: [
		{ resource: "actor", target: { id: sourceId }, operations: ["fork"] },
		{ resource: "actor", target: "any", operations: ["create"] },
	],
});
```

Namespace forks need the admin token. See [Scoped Tokens](/docs/jwt) for issuing tokens with grants.

## Namespace forks

A namespace fork copies a whole namespace into a new one: every actor, with the same actor IDs, keys, and databases as of the fork. Use it for a staging copy of production, or a preview environment with real data. Like an actor fork, it is copy-on-write.

```bash
curl -X POST "$RIVET_API/namespaces?wait=settled" \
  -H "Authorization: Bearer $RIVET_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"staging-copy","fork_from":"production"}'
```

- **Admin only.** Namespace forks need the admin token.
- **Saved writes only.** The fork includes every write the parent acknowledged before the call. `?wait=settled` waits a few more seconds once the fork is live, so writes made after the call usually stay out of the fork. It does not guarantee it.
- **Answers once live.** The new namespace's status is `forking`, then `live`. If that takes longer than 30 seconds, the call answers with the namespace as it stands. Poll `GET /namespaces?name=` until it is `live`.
- **Node pools are not copied.** Create the pools in the new namespace and connect nodes to it before its actors can run. See [Namespaces](/docs/namespaces).
- **`onFork` does not run.** `c.forkChain` stays the same. `c.namespace` returns the new namespace, so an actor that owns something outside Rivet can tell that it is a copy. See [Metadata](/actors/docs/metadata#namespace).
- **Archive forks first.** A namespace cannot be archived while a fork of it is not archived (`namespace.has_forks`).

See [Create Namespace](/docs/api/namespaces/create) for every field and response.

## Limits

| Limit | Value |
| --- | --- |
| Fork depth | 16 forks |
| Namespace fork depth | 3 forks below the original namespace |
| Fork call deadline | 30 seconds, then `actor.fork_pending` |
| `onFork` duration | 5 seconds on the native runtime |
| Fork first start | 15 seconds, including `onFork` |

See [Limits](/actors/docs/limits#forks) for details.
