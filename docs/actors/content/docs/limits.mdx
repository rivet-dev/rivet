This page documents the limits for Rivet Actors.

There are two types of limits:

- **Soft Limit**: Application-level limit, configurable in RivetKit. These cannot exceed the hard limit.
- **Hard Limit**: Infrastructure-level limit that cannot be configured.

### WebSocket

These limits affect actions that use `.connect()` and [low-level WebSockets](/actors/docs/websocket-handler).

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Max incoming message size | 64 KiB | 32 MiB | Maximum size of incoming WebSocket messages. Soft limit configurable via `maxIncomingMessageSize`. |
| Max outgoing message size | 1 MiB | 32 MiB | Maximum size of outgoing WebSocket messages. Soft limit configurable via `maxOutgoingMessageSize`. |
| Max WebSocket frame size | N/A | 32 MiB | Maximum size of a single WebSocket frame accepted by Rivet's transport edge. This is not configurable by browser clients and is not negotiated during the WebSocket handshake. |
| WebSocket open timeout | N/A | 15 seconds | Time allowed for WebSocket connection to be established, including `onBeforeConnect` and `createConnState` hooks. Connection is closed if exceeded. |
| Message ack timeout | N/A | 30 seconds | Time allowed for message acknowledgment before connection is closed. Only relevant in the case of a network issue and does not affect your application. |

WebSocket connections close when the actor sleeps. Clients reconnect, which wakes the actor.

### HTTP

These limits affect actions that do not use `.connect()` and [low-level HTTP requests](/actors/docs/request-handler).

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Max pending buffer size | N/A | 128 MiB | Total size of all buffered messages per connection while actor is sleeping. |
| Max pending message count | N/A | 65,535 | Maximum number of buffered messages per connection while actor is sleeping. |
| Hibernation timeout | N/A | 90 seconds | Maximum time an actor has to wake up before the client is disconnected. Only relevant if something is wrong with starting actors. |

Request bodies are streamed to the actor and have no fixed size limit.

### Queue

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Max request body size | N/A | 20 MiB | Maximum size of HTTP request bodies. |
| Max buffered response body size | N/A | 20 MiB | Maximum size of a non-streaming HTTP response. Streaming responses may transfer more than 20 MiB over their lifetime and are flow controlled instead of buffered in full. |
| Response start timeout | N/A | 5 minutes by default | Maximum time for `onRequest` to return response headers. It does not limit the lifetime of a response stream after the headers arrive. |
| Streaming response idle timeout | N/A | None by default | Rivet does not close an otherwise healthy stream because no body chunk was produced. Other proxies and hosting platforms may impose their own idle timeouts, so SSE handlers should send periodic comment heartbeats. |

### Schedule

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Connection ping timeout | N/A | 30 seconds | Connection is closed if a ping is not acknowledged within this time. Applies to both HTTP and WebSocket. Only relevant in the case of a network issue and does not affect your application. |

### Actor Storage

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Max queue size | 1,000 messages | N/A | Maximum number of messages in the queue before new messages are rejected. Configurable via `maxQueueSize`. |
| Max queue message size | 64 KiB | 128 KiB (effective) | Maximum size of each individual queue message. Configurable via `maxQueueMessageSize`. Actual payload is slightly lower after queue serialization overhead. |

### Actor Storage

Each Rivet Actor has one durable volume. Its [SQLite database](/actors/docs/sqlite) and its [KV](/actors/docs/kv) data live in that volume, so they share one storage limit.

### Actor KV Storage

These limits apply to the [KV API](/actors/docs/kv).

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Max key size | N/A | 2 KiB | Maximum size of a single key. |
| Max value size | N/A | 128 KiB | Maximum size of a single value. |
| Max keys per operation | N/A | 128 | Maximum number of keys in a single batch get/put/delete operation. Does not apply to range operations (`listRange`, `deleteRange`). |
| Max batch put payload size | N/A | 976 KiB | Maximum total size of all key-value pairs in a single batch put operation. |
| Max storage size per actor | N/A | 10 GiB | Maximum total storage of a single Rivet Actor, shared with SQLite. |
| List default limit | N/A | 16,384 | Default maximum number of keys returned by a list operation. |

### Actor SQLite Storage

These limits apply to the [SQLite database](/actors/docs/sqlite). It shares the Rivet Actor's storage limit with KV.

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Max storage size per actor | N/A | 10 GiB | Maximum total storage size for a single actor. This limit is shared with KV storage. |
| Max pages changed per transaction | N/A | 32,768 pages (128 MiB) | Maximum SQLite pages one transaction can change, at 4 KiB per page. A larger transaction fails with `sqlite.transaction_too_large` and is rolled back; the database stays usable. |
| Transaction deadline | 60 seconds | N/A | Safety backstop for `db.transaction()`. Configure per transaction with `{ timeout: milliseconds }`; there is no product-level maximum. |
| Transaction coordinator queue | N/A | 128 operations | Maximum admitted SQLite operations waiting behind an active coordinated transaction. Additional operations fail with `sqlite.transaction_queue_full`. |

Large commits are sent in internal chunks, but each transaction is published atomically. The limit counts raw pages changed, before compression.

If a transaction fails with `sqlite.transaction_too_large`, split the work into smaller transactions, for example by inserting, updating, or deleting rows in batches. `VACUUM` rewrites the whole database in one transaction, so it runs only while the database's in-use pages fit under this limit; it is refused up front on larger databases. Building an index on a large table can also exceed the limit.

### Actor Runtime Socket

The Beta [Actor Runtime Socket](/actors/docs/actor-runtime-socket) negotiates its active frame limit during the handshake.

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Frame payload size | 32 MiB | N/A | Default maximum request or response payload. Self-hosted native runtimes can configure `RIVET_ACTOR_RUNTIME_SOCKET_MAX_FRAME_BYTES`; oversized responses return `ResponseTooLarge`. |

### Startup Preloading

When a Rivet Actor starts, RivetKit loads some of its own data in the same step as the start, to save round trips. Per-actor overrides are set via `options`.

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Max workflow preload size | 128 KiB | N/A | Default maximum size of preloaded workflow data for RivetKit actors. Configurable per actor via `options.preloadMaxWorkflowBytes`. Setting to 0 disables workflow preloading for that actor. |
| Max connections preload size | 64 KiB | N/A | Default maximum size of preloaded connection data for RivetKit actors. Configurable per actor via `options.preloadMaxConnectionsBytes`. Setting to 0 disables connections preloading for that actor. |

### Timeouts

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Action timeout | 60 seconds | N/A | Timeout for RPC actions. Configurable via `actionTimeout`. |
| Raw HTTP response start timeout | N/A | 5 minutes by default | Time allowed for a raw `onRequest` handler to return response headers. `actionTimeout` does not apply to raw HTTP handlers, and a streaming response has no fixed total-duration timeout after it starts. |
| Raw HTTP stream idle timeout | N/A | None by default | Rivet does not close a stream for producing no chunks. Other proxies may, so send SSE heartbeats. |
| On before connect timeout | 5 seconds | N/A | Timeout for the `onBeforeConnect` hook. Configurable via `onBeforeConnectTimeout`. |
| Create vars timeout | 5 seconds | N/A | Timeout for `createVars` hook. Configurable via `createVarsTimeout`. |
| Create conn state timeout | 5 seconds | N/A | Timeout for `createConnState` hook. Configurable via `createConnStateTimeout`. |
| On connect timeout | 5 seconds | N/A | Timeout for `onConnect` hook. Configurable via `onConnectTimeout`. |
| On migrate timeout | 30 seconds | N/A | Timeout for `onMigrate` hook. Configurable via `onMigrateTimeout`. |
| Sleep grace period | 15 seconds | N/A | Total graceful shutdown budget for both sleep and destroy. Covers `onSleep`/`onDestroy`, run handler shutdown, `waitUntil`, `keepAwake`, async raw WebSocket handlers, and connection cleanup. Configurable via `sleepGracePeriod`. |
| Sleep timeout | 30 seconds | N/A | Time of inactivity before actor hibernates. Configurable via `sleepTimeout`. |
| State save interval | 1 second | N/A | Interval between automatic state saves. Configurable via `stateSaveInterval`. |
| Connection liveness timeout | 2.5 seconds | N/A | Time a stateful connection can miss liveness checks before RivetKit treats it as unhealthy. Configurable via `connectionLivenessTimeout`. |
| Connection liveness interval | 5 seconds | N/A | Interval between stateful connection liveness checks. Configurable via `connectionLivenessInterval`. |

### Actor Lifecycle

| Name | Soft Limit | Hard Limit | Description |
|------|------------|------------|-------------|
| Actor start threshold | N/A | 30 seconds | Maximum time for an actor to start before it is considered lost and rescheduled. |
| Actor stop threshold | N/A | 30 minutes | Maximum time for an actor to stop before it is considered lost. |

## Increasing Limits

These limits are sane defaults designed to protect your application from exploits and accidental runaway bugs. If you have a use case that requires different limits, [contact us](/talk-to-an-engineer/) to discuss your requirements.
