## Do You Need Authentication?

<Tabs>
<Tab title="Rivet Cloud">
	Actors are private by default on Rivet Cloud. Only requests with the publishable token can interact with actors.

	- **Backend-only actors**: If your publishable token is only included in your backend, then authentication is not necessary.
	- **Frontend-accessible actors**: If your publishable token is included in your frontend, then implementing authentication is recommended.
</Tab>
<Tab title="Self-Hosted">
	Engine authentication is required by default on self-hosted Rivet. Configure an admin token on the server and issue scoped tokens for clients.

	The explicit `auth.insecure_allow_unauthenticated` Engine setting restores legacy unauthenticated access behavior for trusted networks. Do not enable it on a publicly reachable Engine.
</Tab>
</Tabs>

## Issue Engine Access Tokens

Use a server-side RivetKit client configured with an Engine endpoint and an issuing credential. Engine checks that credential and rejects grants it cannot delegate. These tokens control access to Engine resources; actor connection hooks below can enforce your application's own user authentication as well.

For one actor, use its handle. The default is only `actor_gateway: ["read"]`, scoped to that actor ID:

```ts
const user = client.user.getOrCreate(["user", session.user.id]);
const { token, issuedAt, expiresAt } = await user.issueToken({
  subject: session.user.id,
  expiresIn: 30,
});
```

Supply `permissions` to replace the default. The actor helper accepts `actor_gateway`, `actor`, and `actor_kv` permissions and scopes every grant to the resolved actor ID:

```ts
await user.issueToken({
  subject: session.user.id,
  expiresIn: 60,
  permissions: {
    actor_gateway: ["read"],
    actor: ["read", "update", "delete"],
    actor_kv: ["read"],
  },
});
```

For namespace-wide operations such as actor creation, call `client.auth.issueToken` with an explicit grant list. It never adds permissions automatically:

```ts
await client.auth.issueToken({
  subject: session.user.id,
  grants: [{ resource: "actor", target: "any", operations: ["create"] }],
});
```

`expiresIn` is in seconds; omit it to use Engine's default lifetime. `issuedAt` and `expiresAt` are Unix timestamps in **milliseconds**. Keep the issuing credential on your server and return only the scoped token to the browser.

## Authentication Connections

Authentication is configured through either:

- `onBeforeConnect` for simple pass/fail validation
- `createConnState` when you need to access user data in your actions via `c.conn.state`

## Access Control

After a connection is authenticated, use [Access Control](/actors/docs/access-control) to enforce authorization:

- Check permissions in action handlers.
- Use `queues.<name>.canPublish` to gate inbound queue publishes.
- Use `events.<name>.canSubscribe` to gate event subscriptions.

## Available Auth Data

Authentication hooks have access to several properties:

| Property | Description |
|----------|-------------|
| `params` | Custom data passed by the client when connecting (see [connection params](/actors/docs/connections#extracting-data-from-connection-params)) |
| `c.request` | The underlying HTTP request object |
| `c.request.headers` | Request headers for tokens, API keys (does not work for `.connect()`) |
| `c.state` | Actor state for authorization decisions (see [state](/actors/docs/state)) |
| `c.key` | The actor's key (see [keys](/actors/docs/keys)) |

It's recommended to use `params` instead of `c.request.headers` whenever possible since it works for both HTTP & WebSocket connections.
